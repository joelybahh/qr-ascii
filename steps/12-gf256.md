# 12 Arithmetic in GF(256)

**Goal:** a function that multiplies two bytes the way Reed–Solomon needs.

## The problem

Error correction is what lets a QR code survive a scratch or a bad photo. The scheme is called **Reed–Solomon**, and it does arithmetic on bytes. Ordinary arithmetic won't do, because 200 × 3 doesn't fit in a byte. Reed–Solomon uses a different arithmetic in which every result is still a byte. It's called **GF(256)**.

You need two operations.

**Addition is XOR.** So is subtraction. That's all there is to it.

**Multiplication is the real work.** The trick is the same one a slide rule uses: to multiply, add logarithms.

1. In this arithmetic, every byte except 0 is some power of 2. Call 2 by its traditional name, **α**.
2. Build a table of powers: α⁰ = 1, and each entry is double the one before. When doubling gives a result above 255, XOR it with **285** (`0x11D`) to bring it back into range.
3. Build the reverse table: for each byte, which power of α is it? That's its logarithm.
4. To multiply a and b: look up both logarithms, add them, and look up that power. Anything times 0 is 0.

The powers repeat after 255 steps, not 256. So when you add two logarithms, wrap the sum around at 255.

Build the tables once and keep them.

## Rust you'll meet

- Fixed-size arrays, `[u8; 256]`
- Integer overflow. In debug builds, Rust panics when a `u8` goes above 255. You'll hit this twice in this step, and both times the fix is to think about which type the intermediate value should be
- The XOR operator `^`
- Where to keep a table you build once: in a struct you pass around, or in a `static` with `LazyLock`

## Done when

All the values in the step 12 table of [`checkpoints/README.md`](../checkpoints/README.md) come out right. A few of them:

| Check | Value |
| --- | --- |
| First powers of α | 1, 2, 4, 8, 16, 32, 64, 128, 29, 58, 116, 232, 205 |
| α²⁵⁵ | 1 |
| 128 × 2 | 29 |
| 17 × 236 | 138 |

And these properties hold, each as a test:

- Every value from 1 to 255 appears exactly once among α⁰ to α²⁵⁴
- a × b equals b × a, for every pair
- a × 1 equals a, and a × 0 equals 0, for every a

<details>
<summary>Hints</summary>

- The first eight powers are just doubling. The ninth is 256, which is too big: 256 XOR 285 is 29. That's the pattern for every overflow.
- Do the doubling in a type wider than `u8`, then store the reduced result.
- The sum of two logarithms can be as large as 508. That doesn't fit in a `u8` either.
- The logarithm of 0 doesn't exist. Handle 0 before you touch the tables.
- A neat alternative to wrapping the sum: make the power table twice as long, so the sum can index it directly.

</details>
